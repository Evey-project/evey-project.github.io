    编写插件¶

    本页带开发者从克隆 Evey 开始，到让一个插件在本地服务器上跑起来，再到做出一个其他管理员也能安装的签名包。 第 3 节的教程是最顺利的那条路；其余部分是您以后会回来查的参考。 具体的调用和字段在插件 API 参考里。

    flowchart LR
  subgraph server["Evey 服务器"]
    host["HostService<br/>按声明的权限<br/>检查每一个调用"]
    ui["网页界面<br/>插件插槽"]
  end
  subgraph plugin["插件，在它的沙箱里"]
    backend["PluginService<br/>您的后端进程"]
    front["前端模块<br/>隔离的 iframe"]
  end
  backend <-->|"Unix 套接字上的 gRPC"| host
  front <-->|"postMessage 桥接"| ui
  host -->|"Fetch：只限声明过的主机"| net(("互联网"))

    插件是一个 ZIP 包，根目录里有一个 plugin.yaml，还有一个由服务器在沙箱里启动的后端进程。 这个进程在一个 Unix 套接字上提供一个小小的 gRPC 服务，再通过另一个套接字回头调用服务器。 插件还可以带一个界面模块，显示在页面里一个沙箱化的框架中；它和外界打交道只能经过服务器，而且只能访问它声明过的主机。

    1. 准备工作¶

    工具 用途
    Go 1.27、带 pnpm 的 Node.js 22、带 Compose 的 Docker 开发环境（make dev）要用它们构建服务器和网页应用。
    bubblewrap（bwrap） 只有 bubblewrap 和 strict 沙箱模式才需要。默认的 auto 模式使用 Landlock，在 5.13 或更新的内核上什么都不用装。
    cosign 在分发之前给插件包签名（第 7 节）。开发时用不到。

    从服务器能启动的运行时里选择插件的语言：python、nodejs、php、ruby、lua、bash 和 sh 需要镜像里有对应的解释器； go 提供编译好的二进制文件，需要 native-binary 权限。默认镜像只带 Python；-nodejs 镜像加上了 Node.js，-full 镜像再加上 PHP、Ruby 和 Lua。 如果清单写了镜像里没有的运行时，安装时就会被拒绝，并列出可用的运行时。

    gRPC 约定只有一个文件：proto/plugin/v1/plugin_api.proto。sdk/<language>/ 下有为 Python、Node.js、PHP、Ruby、Dart、Java 和 Swift 生成的存根； 插件启动时，服务器会把对应语言的存根复制到您的入口文件旁边，所以 Node.js 或 Python 插件不需要自带任何依赖： 镜像为 Node.js 插件提供了 @grpc/grpc-js 和 @grpc/proto-loader，为 Python 插件提供了 grpcio。 其他语言请用 protoc 生成存根，并放进 ZIP 包里：

    protoc --proto_path=proto \
       --<lang>_out=OUT_DIR --grpc_<lang>_out=OUT_DIR \
       proto/plugin/v1/plugin_api.proto

    make plugin-sdk 会重新生成随附的存根；每个 sdk/<lang>/README.md 都写明了该语言需要哪个 gRPC 插件。

    2. 在本地启动 Evey¶

    git clone git@github.com:Evey-project/evey.git
cd evey
cp .env.dev.example .env.dev   # 然后设置 MEDIA_DIR、EVEY_DB_PASSWORD、MEILI_MASTER_KEY
make setup                      # 只需一次：把 evey.test 加进 /etc/hosts
make dev                        # postgres、meilisearch、服务器（Air）、网页应用（Vite）

    打开 https://evey.test。第一次启动时，设置向导会创建管理员账户，见首次设置。 插件文件放在 ./evey-data/plugins/<plugin-id>/，在容器里挂载为 /data/plugins。

    3. 一步步写出第一个插件¶

    示例 examples/plugins/nodejs-example 是最小的完整插件：它提供 PluginService，连接 HostService， 并在服务器启动它时往日志里写一行。我们把它复制一份，改一处，然后安装。

    1. 复制示例。

      cp -r examples/plugins/nodejs-example ~/hello-plugin
cd ~/hello-plugin

    2. 给它起个名字。 编辑 plugin.yaml：

      plugin.yaml
      name: hello-plugin          # 唯一，kebab-case 格式
kind: plugin
version: 1.0.0              # semver：每次上传都要调高
description: Says hello in its log
author: you
language: nodejs            # 服务器必须具备的运行时
entrypoint: node main.js    # 服务器执行的命令行
permissions:
  - api.library             # 允许后端读取媒体条目

      language 告诉服务器要检查哪个运行时、复制哪些存根；entrypoint 是它要执行的命令， 在插件的目录里运行，并带有下一步介绍的环境变量。

    3. 读一读 main.js。 服务器给进程传三个变量：EVEY_PLUGIN_ID、EVEY_PLUGIN_SOCK（您的进程必须在这个套接字上监听，提供 PluginService） 和 EVEY_HOST_SOCK（您连接这个套接字来调用 HostService）。示例从自己的目录加载 plugin_api.proto（服务器把它复制到了那里）， 并实现了 PluginService 的五个方法。改一下 Initialize 里的消息：

      main.js（节选）
      Initialize(call, callback) {
  hostLog("LOG_LEVEL_INFO", `hello from ${process.env.EVEY_PLUGIN_ID}`);
  callback(null, { success: true });
},

    4. 打包成 ZIP。 清单必须位于压缩包的根目录，不能放在子目录里：

      zip -r ../hello-plugin.zip . -x ".*" "node_modules/*"

    5. 安装它。 在管理 → 插件里点安装插件，选择 ZIP 包，再点预览并安装：预览会列出 api.library 以及静态分析的结果。 通过 API 进行同样的上传：

      curl -F "plugin=@hello-plugin.zip" \
     -H "Authorization: Bearer $EVEY_TOKEN" \
     https://evey.test/api/v1/admin/plugins/upload

    6. 查看日志。 在插件卡片上，日志会显示 Initialize 写下的那一行。docker compose logs evey 里有同一次启动在服务器这一侧的记录，以插件的 id 标注。

    7. 反复修改。 改代码，调高 version，重新打包，然后在卡片上用从源更新…。版本相同或更低的上传会被拒绝； 清单里新增的权限会触发一个需要管理员批准的同意步骤。

    到这里，您已经掌握了全部的后端约定。接下来，插件可以朝三个方向扩展：调用服务器（HostService，第 4 节）、 画出界面（第 5 节）、与外界通信（第 6 节）。

    4. 从后端调用服务器¶

    每个 HostService 调用都带着插件的身份：服务器根据 PID 检查套接字另一端的进程，一个拦截器会拒绝清单没有声明所需权限的任何调用。 有三组调用完全不需要权限：

    • Log 写入插件的日志，显示在插件卡片上；
    • GetConfig 读取管理员在配置里设置的值（在 config_schema 里声明），SetConfig 让插件在那里保存自己的键；
    • GetData / SetData / DeleteData / ListDataKeys 是插件私有的键值存储，卸载时清空。

    GetMediaItem 和 ListMediaItems 需要 api.library 或 media.read；Fetch 需要 network。 完整的表格，包括约定里已经声明但还没有提供的方法，见 插件 API 参考。

    5. 加上界面¶

    界面是一个 JavaScript 模块，页面把它加载到一个沙箱化的框架里，放在服务器允许的某个插槽中。声明文件在哪里、模块放在哪里：

    plugin.yaml
    web_root: dist               # 作为静态资源提供的目录
frontend:
  - slot: home.section       # 见插槽列表
    src: dist/index.js       # 必须位于 web_root 之下

    模块会拿到一个 window.evey 桥接接口：evey.onInit 把插件的配置、语言区域、主题以及它所在的界面类型交给它； evey.resize、evey.toast 和 evey.navigate 在固定的限度内操作页面；当清单声明了 prefs 或 public 时， evey.prefs.* 和 evey.media.* 会借助宿主为框架持有的一个短期令牌访问服务器。 examples/plugins/weather 是一个带构建步骤的完整小组件；examples/plugins/data-demo 演示了 prefs、public 和 admin.nav 插槽。 桥接接口和插槽的说明见插件 API 参考。

    6. 与外界通信¶

    无论哪种沙箱模式，插件进程都不能打开通向互联网的套接字。唯一的出路是 HostService 的 Fetch 调用： 服务器按清单检查目标，然后由它自己发出请求。

    plugin.yaml
    permissions:
  - network
external_fetch:
  - api.open-meteo.com       # 单纯的主机名：不带协议、不用通配符、不写 IP

    声明了 network 却没有 external_fetch，安装会被拒绝。运行时，代理只接受 http 和 https、GET 和 HEAD， 在 20 秒内返回最多 8 MiB 的响应，并且拒绝私有或保留地址，经过重定向也一样。界面的框架拿到同一份主机列表作为它的 connect-src， 所以小组件可以通过 https 直接调用这些主机。规则见权限与插槽。

    主机列表是您和管理员之间的约定

    管理员在安装时会看到主机列表，更新时新增的任何主机都必须经过批准。只写插件真正需要的主机， 并在 README 里说明每个主机会收到什么。

    7. 给插件签名¶

    签名能证明什么

    签名说明管理员安装的 ZIP 包，和您发布的那个逐字节相同，并且是用他们信任的密钥签的。 它不说明插件做了什么：权限、主机列表和预览里的分析照样适用。Evey 在进程内离线检查签名 （对 ZIP 的 SHA-256 做 ECDSA P-256 签名，也就是 cosign sign-blob --key 生成的格式）： 服务器上不需要 cosign 程序，不联网，也不用透明日志。

    只有您自己的机器上需要 cosign。

    1. 只需一次：生成一对密钥。

      # 请设置一个真正的口令；cosign.key 必须保密，绝不要提交到仓库
COSIGN_PASSWORD="your-passphrase" cosign generate-key-pair
# -> cosign.key（私钥）和 cosign.pub（您分发出去的文件）

    2. 每次发布：先打包，再签名，签的必须是您要分发的那个文件。

      cd hello-plugin && zip -r ../hello-plugin.zip . && cd ..

COSIGN_PASSWORD="your-passphrase" cosign sign-blob \
  --key cosign.key --tlog-upload=false --yes \
  --output-signature hello-plugin.zip.sig \
  hello-plugin.zip

    3. 发出之前先检查，用和服务器相同的验证方式：

      cosign verify-blob --key cosign.pub --signature hello-plugin.zip.sig \
  --insecure-ignore-tlog hello-plugin.zip      # -> Verified OK

    4. 三个文件一起发布：hello-plugin.zip、hello-plugin.zip.sig 和 cosign.pub。 把公钥的指纹放在用户能对照的地方（README、发布说明），这样他们就知道 cosign.pub 没有被调包。

    在要安装插件的服务器上，管理员设置公钥和策略，然后重启服务器：

    EVEY_PLUGINS_COSIGN_PUBLIC_KEY=/etc/evey/cosign.pub
EVEY_PLUGINS_COSIGN_POLICY=warn   # 或者 "enforce"，拒绝验证不通过的包

    之后，在管理 → 插件里选择 ZIP 包，并在签名文件（.zip.sig，可选）里选择对应的 .zip.sig； 通过 API 上传时，签名放在 sig 字段里。预览会显示已签名或签名无效，安全仪表板会保存这个结果。

    容易踩坑的地方：

    • 对 ZIP 包的任何改动都会让签名失效，哪怕只是把同样的文件重新打包。请给您分发的那个文件签名，每个版本都重新签一次。
    • 只接受 ECDSA P-256 密钥，cosign generate-key-pair 生成的正是这种。无密钥签名和 KMS 引用不会被验证。
    • 公钥在启动时从 PEM 文件读取：文件缺失或格式错误，服务器会直接停止，而不是等到第一次安装时才失败。 设为 enforce 却没有公钥时，服务器拒绝启动。
    • 保持默认的 warn 且没有配置公钥时，什么都不会验证；服务器只会在启动时记录一条警告。
    • 密钥不对、ZIP 被篡改、缺少 .sig，都会被当作签名失败：在 enforce 下，安装或更新会被拒绝。

    8. 安装程序依次检查什么¶

    每一步都可能拒绝这个包；管理员会看到原因，服务器日志里有详细信息。

    1. 清单。 直接从 ZIP 包里读取 plugin.yaml：必填字段、semver 版本号、已知的权限和能力、插槽在允许列表里、 external_fetch 的条目是单纯的主机名、声明了 frontend 时有 web_root。声明的 language 必须是镜像里有的运行时。
    2. 版本和权限升级。 对于已经安装的插件，新版本必须更高；任何新增的权限、能力、插槽或主机，都会让安装停在这一步， 直到管理员批准这些差异（上传路由上的 accept_permission_changes=true）。
    3. 签名和哈希。 配置了公钥时会验证签名；只有在 enforce 下，验证失败才会阻止安装。ZIP 包的哈希会被记录下来， 之前预览过的更新在应用时会再核对一次。
    4. 解压到一个临时目录：最多 5,000 个条目，单个文件最大 100 MB，总共最多 500 MB，压缩比不超过 100:1， 不允许符号链接，不允许跑出压缩包范围的路径。在后面每一步都通过之前，更新绝不会动正在运行的版本。
    5. 仅限主题： 样式表会被清理并写回；theme.js 如果匹配到被禁止的模式，整个包会被拒绝。
    6. 对每个文本文件做静态分析：严重级别的发现会拒绝这个包；deserialization 和 obfuscation 警告同样会拒绝； native_code、编译好的二进制文件和内嵌的压缩包也会拒绝，除非清单声明了 native-binary。
    7. 保存并启动。 临时目录被换到正式位置，写入数据库记录，然后启动进程。

    分析会查找什么，列在插件沙箱与威胁模型里。它也会读注释：注释里的一行 # pip install foo 会和代码一样被报告。

    9. 您的进程在什么条件下运行¶

    服务器以较低的 CPU 优先级启动进程，并设置内存上限、进程和线程数量上限，以及目录大小上限； 超出这些限制的插件会被监控程序停掉。默认值是 256 MiB、64 个进程和 100 MiB，管理员可以在管理 → 插件 → 资源限制里调整。 没有 subprocess 权限时，无论用什么语言，进程都不能创建子进程；线程可以正常使用。

    沙箱把文件系统限制在插件自己的目录里，并无条件切断所有网络套接字。生效的是哪种模式，取决于宿主机器，而不是插件： 插件沙箱与威胁模型介绍了各种模式，插件沙箱设置告诉管理员该选哪一种。

    10. 分发插件¶

    没有插件目录商店：管理员在管理面板里上传插件的 ZIP 包，或者粘贴它的网址，来源是您发布它的任何地方（代码托管平台上的一个 release，您自己的网站）。

    • 把 ZIP 包、它的 .sig 和您的 cosign.pub 放在一起发布（第 7 节）。
    • 在 README 里写明权限和 external_fetch 主机：管理员安装时会看到它们，并且必须批准；这里出现意外，是安装被拒绝的头号原因。
    • 如果想让您的插件和自带的示例列在一起，请向 examples/plugins/ 提交一个 pull request，附上源代码和 README。 示例会经过审查，并从源代码构建；被列入并不代表项目背书，也不带项目的签名。

    11. 故障排除¶

    现象 原因 解决办法
    plugin requires "nodejs" runtime which is not installed in this image 这个镜像版本缺少对应的解释器。 使用 -nodejs 或 -full 镜像，或者用 Python 编写插件。
    manifest: external_fetch entry "*.tmdb.org" is a wildcard - use explicit hostnames 安装时一律拒绝通配符，没有例外。 列出您需要的每一个主机名（api.tmdb.org、image.tmdb.org）。
    manifest: frontend slot "admin.section" not allowed 这个插槽不在允许列表里。 从插槽列表里选一个；admin.nav 是管理区域里唯一的插槽。
    manifest: network permission requires non-empty external_fetch 声明了 network 却没有主机。 加上主机，或者去掉这个权限。
    plugin already installed at version 1.0.0, new version must be higher ZIP 包的版本和已安装的相同。 调高 version，或者先卸载。
    signature does not match the plugin or the configured key .sig 是用另一把密钥做的，或者 ZIP 包在签名之后被改过。 用正确的密钥给这个 ZIP 包重新签名，或者修正 EVEY_PLUGINS_COSIGN_PUBLIC_KEY。
    plugin blocked: theme.js contains forbidden pattern 主题脚本扫描器匹配到了被禁止的 API。 主题只能调用 evey.theme.*：见主题。
    日志最后一行是 memory quota exceeded (... MB > ... MB) 插件超出内存上限，被监控程序停掉了。 降低内存用量，或者在资源限制里调高最大内存（MiB）。
    bwrap: ... permission denied 在 Docker 里使用 bubblewrap 模式，被容器的 seccomp 或 AppArmor 配置拦住了。 保持默认的 auto 模式。否则请看插件沙箱设置。
    界面模块没有出现 插件被禁用了、插槽名称拼错了，或者 src 不在 web_root 之下。 检查卡片的状态、插槽名称，以及浏览器网络面板里 /api/v1/plugins/<id>/assets/... 的请求。
